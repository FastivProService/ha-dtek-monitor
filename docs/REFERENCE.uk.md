<a id="entities"></a>
## Як знайти правильні ID сутностей

Відкрийте **Налаштування → Пристрої та служби → DTEK Monitor → ваш пристрій**. Копіюйте ID звідти: назва на екрані та ID сутності — різні речі.

Нові регіональні записи мають стабільний префікс на кшталт `dtek_krem_<address_hash>`. Одеські та старі записи можуть зберігати ID, утворені з початкових назв. Не перейменовуйте сутності лише заради відповідності прикладу. Telegram-бот автоматично знаходить підтримувані префікси.

| Призначення | Типовий суфікс ID; старі ID можуть відрізнятися |
| --- | --- |
| Стан живлення за даними оператора | `binary_sensor.<prefix>_power` |
| Тип відключення | `sensor.<prefix>_outage_status` |
| Опис, початок, завершення | `sensor.<prefix>_outage_description`, `_outage_start`, `_outage_end` |
| Основна/всі групи | `sensor.<prefix>_primary_schedule_group`, `_all_schedule_groups` |
| Час оновлення джерела | `sensor.<prefix>_dtek_last_update`, `_schedule_changed` |
| Діагностика з’єднання | `sensor.<prefix>_dtek_connection` |
| Плановий/можливий графік | `calendar.<prefix>_outage_schedule`, `_possible_outage_schedule` |

Знайдіть **Останній відомий графік — лише перегляд** за відображуваною назвою. Для автоматизацій використовуйте актуальні календарі, збережений — для довідки.

Сенсор живлення має стани `on`/`off`; після помилки запиту адреси стає недоступним. Типи відключень: `ok`, `emergency`, `planned`, `stabilization`. Якщо ДТЕК перелічує кілька активних відключень, основним стає найсерйозніше. Атрибути `outage_N_*` зберігають окремі описи й час.

<a id="freshness"></a>
## Актуальність і календарні автоматизації

Нещодавня зміна стану в HA сама по собі не підтверджує актуальності графіка. На сенсорі групи перевіряйте:

| Атрибут | Значення |
| --- | --- |
| `schedule_groups` | Повний список груп адреси; основна група не обов’язково єдина. |
| `group_labels_visible` | Чи придатні ідентифікатори груп для публічних підписів. |
| `provider_id`, `address_id` | Ідентичність джерела, щоб не змішувати операторів та адреси. |
| `schedule_notifications_ready` | Чи пройшов графік актуальну перевірку адреси й груп. |
| `schedule_snapshot_id` | Ідентифікатор перевіреного знімка графіка. |
| `schedule_coverage` | Опубліковані діапазони дат для кожної групи й типу інтервалів. |

Актуальні календарі та діагностичний сенсор також мають `data_status` (`current`, `stale`, `missing`), `last_verified_at`, `source_updated_at`, `schedule_state`, `schedule_reason`.

Для власних сповіщень про графік:

1. Вимагайте `schedule_notifications_ready == true`.
2. Прочитайте групи, ідентичність джерела та ID знімка, потім отримайте календарні події.
3. Перед надсиланням переконайтеся, що ці значення не змінилися.
4. Зберігайте належність події до групи з опису, наприклад `Planned; group=GPV3.1`.
5. Трактуйте порожній результат як «планових відключень немає» лише за повного покриття потрібних дат для вибраних груп.
6. Не використовуйте календарі/події з `usage=display_only` як актуальне джерело автоматичних сповіщень.

[DTEK Telegram Bot](https://github.com/groove-max/ha-dtek-telegram-bot/blob/main/README.uk.md) уже виконує ці перевірки для повідомлень про графік. Із ним не потрібно повторювати цю логіку у власних автоматизаціях.

Календар може бути доступним, хоча окремі майбутні дати ще не опубліковані. `coverage_start`/`coverage_end` обмежують період збереженого знімка, але **не означають публікацію кожного дня всередині**. Покриття публікації визначає `schedule_coverage`. Запит повністю поза ним завершується помилкою, а не повідомленням про відсутність відключень.

Розрахунки графіка виконуються в часовому поясі Києва; межі запиту HA можуть містити інший часовий пояс, зокрема UTC. Можливі інтервали відображаються лише за наявності відповідних опублікованих даних. Старі тижневі шаблони не продовжуються нескінченно.

### Стан публікації відрізняється від помилки запиту

**З’єднання ДТЕК = OK** означає, що запити та перевірка відповідей успішні.
Окремий сенсор **Доступність графіка** описує планові відключення на сьогодні:

| Стан | Значення |
| --- | --- |
| `current` | Повний підтверджений графік містить планові відключення сьогодні. |
| `empty` | Для всіх груп є повні дані за день, планових відключень немає. |
| `forecast` | Є лише прогноз; він не підтверджує планові відключення. |
| `partial` | Дані неповні; пропущені проміжки не означають наявність світла. |
| `missing` | Повного застосовного графіка не підтверджено. |
| `unpublished` | ДТЕК явно вимкнув публікацію. |
| `unsupported` | Адреса належить непідтримуваному оператору. |
| `error` | Помилка запиту адреси/графіка або некоректна відповідь. |

`status_date` і `status_timezone` визначають день у Europe/Kyiv. Це стан графіка,
а не фактичної наявності світла. Відсутність публікації не збільшує лічильник
помилок зв’язку. Звичайні календарі HA залишаються `unavailable`, якщо придатного
графіка немає; окремий статус пояснює причину. Збережені раніше події залишаються
довідковими й не підтверджують відсутність відключень.

### Картка графіка

Додайте `/dtek_monitor/schedule-card.js?v=1.8.0b9` як **JavaScript module** у
**Налаштування → Панелі → Ресурси** (розширений режим), потім ручну картку:

```yaml
type: custom:dtek-schedule-card
title: Будинок — усі групи
status_entity: sensor.example_schedule_availability
entities:
  - calendar.example_outage_schedule
  - calendar.example_possible_outage_schedule
```

Підставте ID сутностей свого пристрою. Для квартири додайте другу картку із
сенсором **Стан мого графіка** та особистими календарями. Картка будинку зберігає
всі групи для бота. Вона використовує українські/англійські пояснення та
стандартний календар HA; автоматизації й особистий вибір не змінюються.

### Збережені графіки

Успішна повна перевірка зберігає конкретні події на восьмиденний період у сховищі Home Assistant. Успішна відповідь без змін оновлює час перевірки; невдалий запит — ні. Завантаження знімка після перезапуску не робить актуальними основні сенсори й календарі. Винятку «старі дані ще свіжі протягом 45 хвилин» немає.

<a id="diagnostics"></a>
## Діагностика недоступних даних

Відкрийте діагностику з’єднання ДТЕК на сторінці пристрою та її атрибути:

- `address_last_success`, `address_error`: запити адреси/поточного стану.
- `schedule_last_success`, `schedule_error`: запити графіка.
- `last_success`, `last_error`, `consecutive_failures`: загальний стан опитування.
- `retry_interval_seconds`: поточний інтервал повторних спроб.
- `snapshot_storage_error`: помилки збереження/читання довідкової копії.

Повторні помилки видно в діагностиці, навіть коли решта сутностей недоступна. Після збоїв інтервал повторів зростає приблизно до 1, 2, 4, 8 і 10 хвилин із невеликим розкидом. Успішний запит повертає налаштований інтервал.

Перевірте ту саму адресу на сайті оператора. Якщо він також не працює, дочекайтеся відновлення джерела. Якщо сайт працює, перегляньте журнали HA за назвою інтеграції: помилки з’єднання, захисту сайту або обробки відповіді. Не зменшуйте інтервал опитування для обходу захисту сайту.

У повідомленні про проблему вкажіть версії, оператора, час із часовим поясом і текст помилки без приватних даних. Журнали та знімки екрана можуть містити точну адресу — вилучіть те, чого не хочете публікувати.

<a id="updates"></a>
## Оновлення, резервні копії та видалення

1. Перед оновленням створіть резервну копію Home Assistant.
2. Прочитайте [історію змін](../CHANGELOG.md), оновіть через HACS або замініть папку інтеграції та перезапустіть HA.
3. Перевірте з’єднання, адресу та календарі. Оновіть Telegram-бота, якщо його випуск потребує новіших атрибутів інтеграції.

Наявні записи мігрують автоматично; поточна версія схеми запису — 3. Адресна ідентичність призначена для збереження ID після оновлень. Ручні перейменування мають пріоритет. Видалення та повторне додавання адреси не є звичайним кроком оновлення.

Повна резервна копія HA зберігає записи конфігурації, реєстри сутностей і знімки графіків. Не редагуйте `.storage` вручну. Після видалення запису інтеграції його активні сутності більше не використовуються; відповідно змініть панелі, автоматизації та адреси бота.

<a id="architecture"></a>
## Звідки беруться дані

Інтеграція читає публічний сайт відключень обраного оператора. Це не гарантований публічний API ДТЕК: зміни сайту можуть потребувати оновлення інтеграції.

| Модуль | Відповідальність |
| --- | --- |
| `providers.py` | Підтримувані оператори та адреси їхніх сервісів. |
| `provider.py` | Інтерфейс постачальника й нормалізовані типи адрес/графіків. |
| `dtek_provider.py`, `dtek_client.py` | Звернення до сайту ДТЕК та нормалізація відповідей. |
| `config_flow.py` | Вибір оператора/адреси та параметри опитування. |
| `coordinator.py` | Оновлення, перевірка, повтори та діагностика. |
| `schedule.py`, `snapshot.py` | Правила інтервалів, покриття публікації та збережені дані. |
| `sensor.py`, `binary_sensor.py`, `calendar.py` | Сутності HA. |

Про розробку та перевірки — у [посібнику учасника](../CONTRIBUTING.uk.md).
